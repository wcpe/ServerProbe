# 功能规格：告警规则扩面与告警历史落盘

> 状态：开发中　·　关联 PRD：FR-29（增强 FR-05）　·　分支：feature/alert-extended

## 1. 背景与目标

FR-05 告警只有 4 种规则类型（TPS 低 / MSPT 高 / 堆占用高 / 死锁），且**告警触发后无历史可查**——"昨晚响过几次、后来恢复了吗"只能翻日志，无法事故回溯。另有一处文档漂移：wiki（Data-Output.md）宣称存在"GC 频繁 / 启动超基线"规则，代码中并不存在。本 FR 扩规则类型 + 补告警历史落盘与查询，并把 wiki 宣称的两类规则做成真的。

## 2. 需求（要什么）

- **新增规则类型**（沿用 `AlertType` 枚举多态，extract/violated 两方法即可接入引擎与配置解析）：
  - `GC_OLD_HIGH`：老年代 GC 频率/单次耗时超阈（数据源 `MetricSnapshot` 既有 GC 速率聚合；口径实现时对齐 AggregatedMetrics 字段）。
  - `STARTUP_SLOW`：最近一次启动总耗时超基线倍数（默认 ×1.5，数据源启动画像总时长）。
- **告警历史落盘**：触发/恢复事件按既有 JSONL + 按日滚动 + 保留天数 + 体积上限双闸机制落盘（复用 store 既有设施，原子写/异步写红线不破）。
- **查询出口**：`/probe alerts` 子命令展示最近 N 条告警事件（时间/类型/级别/状态：触发中|已恢复|已静默）；Web 面板不扩页（YAGNI，历史页留待后续按需）。
- 范围内：core（alert 类型 + 落盘 + 查询 API + `/probe` 子命令）+ lang 键 + 单测 + 文档。
- 不做（范围外）：
  - 不做告警静默窗口/按级别路由（运维刚需但独立成项，避免本 FR 膨胀）。
  - 不做 Prometheus 告警指标导出（模板侧由 FR-27 承担）。
  - 历史不含通知投递结果明细（只记引擎事件本身）。

## 3. 设计（怎么做）

- `AlertType` 加两个枚举常量（类 KDoc 自述"新增类型只需加常量"的设计意图）；`RuleSpec` 补对应规则与默认阈值；`ProbeConfig.alertRules()` 的命名规则映射随之扩面（`alert.rules.<name>.type` 支持新枚举值）。
- 历史落盘：`MetricStore`/独立 writer 二选一在实现期定（倾向独立轻量 writer，避免把告警语义塞进指标存储 SPI 造成 SPI 兼容负担）；格式 `{tsMs, type, level, action, value, threshold}`。
- 查询：core 只读 API 或直接命令层读文件（实现期定，倾向命令层直读最近文件避免公开 API 面扩张）。
- 启动慢告警的数据可用性：无画像（如代理端）时该类型规则跳过判定，与引擎"数据缺失只清状态不误报"语义一致。

## 5. 验收标准

- 单测全绿：两新类型边界（阈值恰好/持续周期防抖/数据缺失不误报）、历史按日分桶与保留清理、`/probe alerts` 输出。
- 真机（Paper）：压低 TPS 触发告警 → `/probe alerts` 可见事件 → 恢复后事件状态更新；GC 规则用真实 GC 数据验证判定；启动慢规则在人工制造慢启动（大插件集）下触发一次。
- 真机：告警历史文件按日滚动、过期清理生效，当天文件绝不被清（沿用既有红线判据）。
- 中文日志与 i18n：新 lang 键中英一致。

## 6. 风险 / 待定

- `GC_OLD_HIGH` 的口径需实现期对齐 `AggregatedMetrics` 的 GC 速率字段精度（避免阈值语义含糊）。
- 历史落盘走独立 writer 还是并入 MetricStore：倾向前者，若实现中发现复用价值高再调整（不影响对外行为）。
