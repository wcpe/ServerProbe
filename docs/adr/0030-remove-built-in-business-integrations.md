# ADR-0030：移除内置业务集成模块，改由插件自注册

## 状态

已接受，**取代 ADR-0016、ADR-0017、ADR-0018**（实现见
[business-self-registration spec](../specs/business-self-registration.md)，PRD 记账为 FR-37／取代 FR-10）

## 背景

探针曾内置两个业务集成模块（`integration-multicurrencyeconomy`、
`integration-allininventorysync`，合计约 2200 行），直接 `compileOnly` 依赖第三方业务插件的 API，
把它们的业务语义（金额、货币、物品、NBT）硬编码进探针。

这带来三个不可持续的问题：

1. **探针变成业务插件的一部分**。每接一个新业务插件就要改探针、发版、等升级；
   第三方插件的 API 一改，探针跟着编译失败。
2. **内置实现与外部接入不平等**。内置模块走内部容器，第三方只能反射，
   而"能不能接入"取决于探针作者愿不愿意写那个模块。
3. **私有格式污染契约**。`EconomyEnvelope` / `InventoryEnvelope` 的字段映射
   被当成了协议的一部分，而它们只是某两个插件某两个版本的载荷结构。

ADR-0016/0017/0018 当时的判断（在探针内做降级封装、以字节门面兼容多版本）在其前提下是合理的，
但那个前提——"探针应当内置业务实现"——已被推翻。

## 决策

**彻底删除**两个内置集成模块及其全部配套（E2E 场景、模板配置、离线运行时闭包、spec、文档引用），
探针只做「业务面板（JM CP）↔ 插件」的**路由中介**；业务域由插件经
`ServerProbeAPI.businessHost().register(...)` 自行注册。

配套硬边界：

- `api` 模块**禁止绑定任何第三方私有格式**：不出现第三方插件名、不出现专有字段名
  （金额/货币/物品/属性/任何序列化载荷结构）、不出现第三方 API 类型；
- 原 `EconomyEnvelope` / `InventoryEnvelope` 的字段映射**随模块一起删除，
  不在任何地方保留副本**（含文档、示例、测试 fixture），最终形态只存在于 git 历史；
- 本仓**不提供、也不维护任何具体域的协议说明表**——具体字段由各插件在自己的
  `manifest()` 中声明，探针不解释、不校验。

## 理由

- **依赖方向变干净**：`api` 与 `core` 的依赖树里不再有任何业务插件坐标，
  插件只依赖 `ServerProbe-api`（`compileOnly`），而 `api` 不依赖任何业务插件——单向且无环。
- **接入能力不再由探针作者分配**：自注册是公开路径，任何插件都能走，
  不再需要"请探针作者加一个模块"。
- **保留 `Envelope` 类字段映射是不可行的折中**：只要它在仓里，就会被当成协议读，
  于是探针又要为一个自己不理解的结构负责。删干净比留下"参考实现"更诚实。
- **顺序不可颠倒**：删除的前提是自注册门面已可用（ADR-0029）。
  若先删，会出现一段"既无内置、也无外部接入"的空窗，业务域归零。

## 后果

- **破坏性变更**：升级后 `jbis/manifest` 暂不含 `economy` / `inventory` 域，直到业务插件自注册。
  空 manifest（`{"domains":{}}`）是**正常态**，不是故障——需要面板侧确认不误报。
- **升级顺序有硬约束**：首选探针与新插件在同一次重启中一起替换；只能分批时必须
  **先升探针、后升插件**（旧插件不自注册，域短期缺失但服务不崩）；
  反序会让旧插件引用到已删除的 API 类型而 `NoClassDefFoundError`。
- E2E 的"装哪些插件"这一维度消失（原 `both`/`mce-only`/`ais-only`/`none` 四场景随之删除），
  改为按**自注册的生命周期与故障面**设计场景：`self-register-both` / `-single` / `-reload` / `-none`。
- `plugin` 的 `description.dependencies` 里对应的 `optional(true)` 软依赖声明一并移除；
  `bundle` 的"内置集成必须存在"校验**反转为"禁止存在"**断言，防止旧产物回流。
- 本决策**不可逆地**放弃了"开箱即用"：新装用户不再自动获得经济/背包面板数据，
  必须先装对应业务插件。这是刻意用便利性换取边界的清晰度。

## 备选方案

- **保留模块但改为可选下载**：仍需维护两个模块、跟随第三方 API 版本，问题 1、2 未解决。
- **把 `Envelope` 的字段映射迁进 `api.protocol` 供第三方复用**：直接违反"`api` 不得绑定
  第三方私有格式"这条硬约束，且会把探针重新绑上那两个插件的载荷结构。已明确否决。
- **只删实现、留兼容包装层**：会留下"看起来支持、实际已无实现"的假象，
  比直接删除更容易误导运维。
