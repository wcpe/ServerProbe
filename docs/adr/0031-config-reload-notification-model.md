# ADR-31：配置重载的通知-认领模型

## 状态

已接受（FR-32）。

> 术语更正：`docs/specs/config-reload.md` 正文多处写作「ADR-30」，但本仓 ADR-30 已被
> 「移除内置业务集成模块」占用。本决策的正确编号是 **ADR-31**，规格正文的历史编号属漂移，
> 未回改规格（避免与其它并行批次冲突），以此处为准。

## 背景

JianManager（JM）改完某插件配置后，需要让**该插件重新加载**。宿主（服务端）不掌握任何
"配置语义"，因此这件事只能由插件自己做。探针（ServerProbe）处在 JM 与插件之间，可选的三条路：

1. **探针读写并下发配置**：探针成为配置真源 —— 越界。配置的分层、版本、灰度、回滚归 JM CP/Worker，
   探针一旦持有配置内容，就要替所有插件理解格式（YAML/TOML/自定义）。
2. **探针推断是否生效**：探针重载后检查文件 mtime 或插件内部状态 —— 不可行。`reload` 成功
   **不等于**配置生效（插件可能只重读了部分段、可能把错误吞掉、可能延迟应用）。
3. **探针只做通知与收集**：把"这份配置变了"通知给**声明过关心它**的插件，让它自己重载并**自报结果**，
   探针如实转达、不推断。

选 3。随之而来的四个工程问题必须在本决策里定死，否则实现层会各自发明：

- 谁来执行（线程与池）；
- 同一路径被重复下发时怎么办（并发与幂等）；
- 插件卡死时探针能做什么（Java 无法强杀线程）；
- 回执怎么表达"部分成功""无人认领""超时"这些**互不相同**的事实。

## 决策

**采用「通知-认领」模型**：`core.config_reload(payload={"paths":[…]})` 只做
「规范化 → 准入 → 匹配声明 → 回调 → 收集 → 结构化回执」，绝不推断生效。

配套五条硬约束（实现必须逐条满足）：

1. **两池分离**：编排跑 `serverprobe-reload-N`，监听器子任务跑 `serverprobe-reload-worker-N`。
   共用同一个有界池会**池内自锁**——并发请求各占一个协调槽后把子任务推进同一队列，
   队列满即无空闲线程，编排线程全部阻塞在自己提交的任务上，于是全部误判 `TIMEOUT`。
   "轮转收割"是收口算法，救不了池内自锁。
2. **先全部提交、再轮转收割**：批量提交让总耗时等于"最慢的那个"；收割时先非阻塞收全部已落定项，
   再对未完成项按剩余预算分片（≤10ms）轮询，绝不按顺序死等第一个。
3. **在途占用的 `release` 只由任务自身 `finally` 执行**：编排器超时后**不代它释放**。
   `Future.cancel(true)` 对不响应中断的任务无效，代释放会让同路径的第二份重载与仍在跑的第一份
   并发写插件状态。代价是"永不返回的任务长期占位"，因此另设 `STUCK` 错误码（超过
   `stuck-after-ms` 时返回它，而不是继续用 `IN_FLIGHT` 掩盖卡死）。
4. **只有 `TIMEOUT` 触发熔断**，且熔断恢复用**指数退避**：`min(base × 2^(N-1), max)`，
   成功一次即清零。`FILE_NOT_FOUND`/`PARSE_ERROR`/`PLUGIN_REJECTED`/`PATH_ESCAPE`/`IN_FLIGHT`/`STUCK`
   都是确定性结果，重试有意义，不该被熔断沉默。熔断表满了**拒绝新条目**（计入 `rejectedEntries`），
   **不淘汰已有**——淘汰最旧等于"用大量不同 path 就能悄悄解除熔断"。
5. **回执的成败判定只有一条式子**：`success = failed.isEmpty() && error.isEmpty()`。
   无人认领的路径进 `bestEffort`（**算成功**，但单列，让 JM 能显式标注"通知已发出、无人确认"）。

## 理由

- **不推断生效**是唯一诚实的语义。任何推断都会在"插件部分生效"时给出错误结论，而错误结论比
  没有结论更危险：JM 会据此跳过回滚。
- **集合通知 + 结构化结果**能表达单路径 + 单字符串返回值无法表达的四件事：多路径批量、
  无人认领、结构化错误码、自报实际加载内容（`md5`/`version`/`count`）。
- **两池分离**是"重载最容易卡住"这一事实的直接推论：重载回调会进第三方插件，
  其中包含"回主线程读文件"这类可能卡满一个预算的操作。让它可以卡，但不能把编排也一起卡住。
- **`release` 归任务自身**把"不并发"这条不变量变成可断言的事实：宁可长期占位并诚实报 `STUCK`，
  也不要为了腾出路径而制造并发写。
- **只 TIMEOUT 熔断**避免"熔断吃掉真实错误"：配置语法错了应该每次都明确报 `PARSE_ERROR`，
  而不是第二次开始变成 `TIMEOUT`。
- **满则拒绝新条目**选保守方向：漏记一个熔断（该路径仍会执行、可能再次卡住，但被单次超时兜住）
  比误熔断（放行了本该被挡的路径）安全。

## 后果

正面：

- 探针不需要理解任何插件配置格式；新增插件零成本接入（实现 `ConfigReloadListener` 即可）。
- 回执可被 JM 直接渲染：`reloaded`/`bestEffort`/`failed[]`/`applied`/`costMs` 各自语义独立。
- 重载卡死不会传染治理通道：`bridge_status` 等命令仍在命令池上正常返回。
- 重复下发幂等：同路径、同监听器集合、连续两次成功重载，除 `costMs` 外所有回执字段逐项相等。

负面与已知上限（都是本次接受的取舍）：

- **超时后仍在执行**：Java 无法强杀线程，一次超时的重载会继续占用插件侧资源（Bukkit 下可能是主线程）。
  缓解是熔断指数退避（越来越不常被碰）+ `STUCK` 暴露卡死路径；**无法根除**。
- **`plugins/` 限定过严**：把配置放在自定义目录的插件无法接入。后续可加白名单根，
  本轮不做，避免扩大攻击面。
- **无人认领算成功**是产品决策，风险是 JM 误以为已生效；字段名 `bestEffort` 已尽量自解释，
  JM 展示层必须显式标注。
- **`stuck-after-ms` 短于该值的卡死仍报 `IN_FLIGHT`**：取值需与 `timeout-ms` 联动（建议 ≥ 6×）。
- **失败与结构化回执并存**（已决策）：`BridgeCommandResult` 原有的 `ok(output)/fail(error)`
  两个工厂互斥，单靠它们无法同时携带"结构化回执"与"失败原因"，而规格要求失败时
  `reloaded` 仍如实列出成功部分。已增补 `BridgeCommandResult.ofFailure(output, error)`
  （`success=false` 且 `output`/`error` 都可非空），`config_reload` 失败时两个字段都填。
  这是**纯追加**的 api 演进，既有调用方语义不变。面板应优先读 `output`，`error` 供展示与告警。
- **`PlatformReloadExecutor` 暂无树内调用方**：规格明确它"只提供给需要的监听器"，
  但 `api` 契约没有暴露取得途径（监听器自行切主线程即可）。当前作为统一入口保留，
  平台实现已就位（Bukkit 切主线程 + 有界等待，Bungee/Velocity 直通）。

## 备选方案

- **`ConfigReloadHandler.reloadConfig(path): String?`（单路径 + 单返回值）**：落选。
  无法表达多路径批量、无人认领、结构化错误码与自报内容；`String?` 会把"失败原因"与"输出"
  混成一个字段，JM 只能靠字符串约定解析。
- **监听器子任务与编排共用 `serverprobe-reload` 池**：落选。池内自锁（见决策 1），
  表现为高并发时全部 `TIMEOUT`，且现象与"插件真的慢"完全一样，极难定位。
- **编排器超时后 `release` 路径**：落选。制造并发写插件状态，比"占位 + 报 STUCK"危险得多。
- **熔断容量满时淘汰最旧条目**：落选。等于给出"绕开熔断"的廉价手段。
- **熔断恢复用固定窗口**：落选。固定到期即恢复会让病态插件**周期性**重复"卡满一个预算"，
  指数退避让越来越不常被碰。
- **探针代插件切主线程执行回调**：落选。插件才知道自己需要哪个线程；统一代切会把
  Bukkit 上所有回调串行化到主线程，反而放大单插件卡死的影响面。
